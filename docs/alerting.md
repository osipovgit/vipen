# Оповещения в Telegram

Мониторинг проверяет сервер каждую минуту и пишет результат в journald. Проблема в том, что журнал никто не читает: если VPN упадёт ночью, вы узнаете об этом, когда попробуете им воспользоваться.

Эта страница описывает push-уведомления: сервер сам пишет вам в Telegram, когда состояние меняется.

**Важное ограничение.** Уведомления отправляет сам сервер. Если сервер выключен, потерял сеть или его убил хостинг — сообщения не будет, потому что отправлять его некому. Этот случай закрывается отдельным механизмом (dead man's switch), он появится позже. Пока держите в голове: **молчание не означает, что всё хорошо.**

## Кто отправляет сообщения

Сообщения приходят от **бота, которого вы создаёте сами**. Это не сторонний сервис и не общий бот проекта: токен ваш, бот ваш, сообщения идут напрямую с вашего сервера в Telegram API. Никакой промежуточной инфраструктуры между сервером и вами нет.

## Что попадает в FAIL, а что в WARN

Это два принципиально разных класса событий.

### 🔴 FAIL — VPN не работает

Проверка ставит `FAIL`, когда сервис сломан. Тут нужно вмешательство.

| Событие | Что произошло |
|---|---|
| `container <имя> not running` | Контейнер 3x-ui остановлен или упал |
| `docker command missing` | Docker пропал с сервера |
| `panel tcp 127.0.0.1:<порт> unavailable` | Панель не отвечает на локальном порту |
| `local tcp 127.0.0.1:<порт> unavailable` | VPN-порт (443, 8443 или 2096) не слушает |
| `xray process missing inside container` | Контейнер жив, но процесс Xray внутри умер |
| `disk_used >= 95%` | Диск заполнен критически |

Самый коварный здесь — предпоследний: контейнер выглядит здоровым, `docker ps` показывает `Up`, а VPN не работает, потому что внутри умер Xray. Без этой проверки такое состояние можно не замечать сутками.

### 🟡 WARN — работает, но ухудшается

`WARN` означает, что VPN функционирует, но что-то идёт не туда. Реагировать нужно, но не срочно и не ночью.

| Событие | Порог | Что означает |
|---|---|---|
| `disk_used` | ≥ 85% | Диск заполняется. При 95% станет `FAIL` |
| `mem_available` | < 128 МБ | Память на исходе, риск OOM |
| `conntrack` | ≥ 75% от максимума | Таблица соединений заполняется; при переполнении соединения начнут рваться |
| `hypervisor_pause_detected` | — | Ядро зафиксировало `clocksource: Long readout interval` за последние 2 минуты: гипервизор придержал вашу VM |

Последний пункт — не ваша вина и не поломка сервера. Это признак проблем на стороне хостинга, и именно эти строки стоит собирать, если будете предъявлять претензию провайдеру.

### Что не меняет статус

В сообщение попадает, но само по себе тревогу не поднимает: количество перезапусков контейнера, число установленных соединений, `load1`, успешные проверки портов. Это контекст, который помогает понять картину.

### Приоритет

Если одновременно сработали и `WARN`, и `FAIL`, статус будет `FAIL`. Понижения не происходит: `WARN` может поднять статус только с `OK`.

### 📊 Дневной отчёт о гипервизоре

Отдельный монитор `vps-host-monitor` следит за CPU steal и задержками планировщика и пишет свои `status=WARN` раз в 5 секунд. Подключить его к уведомлениям «как есть» нельзя: плохая ночь у хостинга — это сотни сообщений в час.

Поэтому он ходит через дайджест. После полуночи сервер разбирает журнал за **закончившийся день** и присылает **одно** сообщение:

```
📊 vipen: hypervisor anomalies on 2026-07-18

Anomalies: 5 (from 03:14:07 to 22:41:33)
Peak scheduler delay: 8300 ms
Peak CPU steal: 31.07%
By hour: 03:00 x3 04:00 x1 22:00 x1

Details: journalctl -t vps-host-monitor --since "2026-07-18 00:00" --until "2026-07-18 23:59"

2026-07-19 00:02:14 UTC
```

Ограничитель частоты здесь не настройка, а сама конструкция: **больше одного сообщения в день эта ветка отправить не может**. День без аномалий не шлёт ничего, поэтому пришедший отчёт всегда означает, что было что показать.

Разбивка по часам — главное в отчёте. Она отвечает на вопрос, который задаст хостинг: это был один всплеск или всю ночь колбасило.

Отношение к `hypervisor_pause_detected` из таблицы `WARN` выше: тот приходит сразу, но видит только грубые паузы ядра и только за последние 2 минуты. Дайджест приходит с задержкой, зато показывает весь день целиком. Одно не заменяет другое.

Дайджест не трогает состояние health-check: отчёт — не смена состояния, и следующую настоящую тревогу он не проглотит.

## Правила против спама

Проверка идёт раз в минуту. Наивная реализация прислала бы 60 сообщений в час, поэтому действуют ограничения:

- **Сообщение только при смене состояния.** `OK` → `FAIL` шлёт тревогу, `FAIL` → `OK` шлёт восстановление. Пока состояние не меняется, повторов почти нет.
- **`FAIL` требует подтверждения.** Нужно `vpn_monitor_alert_fail_after` неудачных проверок подряд (по умолчанию 2, то есть «всё ещё сломано минуту спустя»). Это отсекает одиночные сбои вроде подтормозившего `docker exec`.
- **Повторы редкие.** Пока проблема держится, напоминание приходит не чаще раза в час для `FAIL` и раза в 6 часов для `WARN`.
- **Здоровый сервер молчит полностью.** Никаких «всё в порядке» каждую минуту.
- **Состояние хранится в `/run`**, то есть сбрасывается при перезагрузке. Это осознанно: после ребута вы хотите получить свежее уведомление, а не тишину из-за старого состояния.

Диагностический режим (`vpn-health-check --no-restart`, его использует ручной healthcheck) уведомления не шлёт вообще — ручная проверка не должна никого будить.

## Настройка

### Шаг 1. Создайте бота

1. Откройте в Telegram [@BotFather](https://t.me/BotFather).
2. Отправьте `/newbot`.
3. Задайте имя (любое) и username (должен заканчиваться на `bot`).
4. BotFather пришлёт токен вида `1234567890:AAHdqTcvCH1vGWJxfSeofSAs0K5PALDsaw`.

**Токен — это пароль.** Кто им владеет, тот может писать от имени вашего бота и читать его переписку. Не публикуйте, не отправляйте в чат, не коммитьте.

### Шаг 2. Начните диалог с ботом

Откройте своего бота и нажмите **Start** (или отправьте любое сообщение).

Это обязательно: **Telegram запрещает ботам писать первыми**. Пока вы не начали диалог, отправка будет падать с ошибкой `403: bot can't initiate conversation with a user`.

### Шаг 3. Узнайте chat_id

Отправив боту сообщение, выполните на своей машине:

```bash
curl -s "https://api.telegram.org/bot<ВАШ_ТОКЕН>/getUpdates" | python3 -m json.tool
```

Найдите в ответе `"chat": {"id": ...}`. Это и есть `chat_id`.

- Личный чат: положительное число, например `123456789`.
- Группа или канал: отрицательное, например `-1001234567890`. Бота нужно добавить в группу, а затем написать туда сообщение, чтобы чат появился в `getUpdates`.

Если `getUpdates` вернул пустой `result`, значит шаг 2 не выполнен — напишите боту и повторите.

### Шаг 4. Заполните и зашифруйте secrets.yml

```bash
cp inventories/production/secrets.example.yml \
   inventories/production/secrets.yml
```

Впишите токен и chat_id, затем зашифруйте:

```bash
ansible-vault encrypt inventories/production/secrets.yml
```

Vault попросит придумать пароль. Запомните его — без пароля файл не расшифровать, и восстановить его нельзя.

Файл `secrets.yml` уже в `.gitignore`. Шифрование поверх этого — защита в глубину: репозиторий лежит в `~/Documents`, а такие каталоги часто синхронизируются с iCloud или попадают в бэкапы, куда открытый токен утекать не должен.

Проверить, что получилось:

```bash
ansible-vault view inventories/production/secrets.yml
```

Позже отредактировать без расшифровки на диск:

```bash
ansible-vault edit inventories/production/secrets.yml
```

### Шаг 5. Примените

```bash
ansible-playbook site.yml --tags monitor --ask-vault-pass
```

Если надоедает вводить пароль вручную, положите его в файл (он уже в `.gitignore`):

```bash
echo 'ваш-vault-пароль' > .vault_pass
chmod 600 .vault_pass
ansible-playbook site.yml --tags monitor --vault-password-file .vault_pass
```

Учтите: файл с паролем на диске обесценивает шифрование, если украдут ноутбук целиком. Для домашней машины приемлемо, для общей — нет.

### Шаг 6. Проверьте

```bash
ssh -i ~/.ssh/vipen root@<IP-сервера> /usr/local/sbin/vpn-notify --test
```

Должно прийти сообщение в Telegram и вывестись `vpn-notify: test message delivered`. При ошибке скрипт объяснит причину — токен пуст, файла нет, Telegram отверг запрос.

## Как выглядит сообщение

```
🔴 vipen: VPN FAIL

container=3xui_app running restart_count=0 panel_tcp=127.0.0.1:<порт> ok
local tcp 127.0.0.1:443 unavailable xray_process=ok disk_used=54%

2026-07-19 03:14:07 UTC
```

При восстановлении:

```
🟢 vipen: recovered

Previous state: FAIL
status=OK failures=0 container=3xui_app running ...

2026-07-19 03:22:11 UTC
```

Секретов в сообщениях нет: только порты, имя контейнера, проценты и счётчики. Путь панели, subscription-ссылка, UUID клиентов и ключи туда не попадают.

## Параметры

Всё несекретное — в `inventories/production/group_vars/vpn_servers.yml`:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `vpn_monitor_alert_enabled` | `true` | Главный выключатель |
| `vpn_monitor_alert_on_fail` | `true` | Слать при `FAIL` |
| `vpn_monitor_alert_on_warn` | `true` | Слать при `WARN` |
| `vpn_monitor_alert_fail_after` | `2` | Сколько неудачных проверок подряд до тревоги |
| `vpn_monitor_alert_repeat_fail_seconds` | `3600` | Повтор при длящемся `FAIL` |
| `vpn_monitor_alert_repeat_warn_seconds` | `21600` | Повтор при длящемся `WARN` |
| `vpn_monitor_alert_timeout_seconds` | `10` | Таймаут запроса к Telegram |
| `vpn_monitor_host_daily_enabled` | `true` | Дневной отчёт о гипервизоре |
| `vpn_monitor_host_daily_schedule` | `*-*-* 00:00:00` | Когда слать отчёт (`OnCalendar`, плюс разброс до 5 минут) |

Секретное — только в `secrets.yml`: `vpn_monitor_alert_telegram_token` и `vpn_monitor_alert_telegram_chat_id`.

Если `WARN` кажется вам шумным, поставьте `vpn_monitor_alert_on_warn: false` — `FAIL` продолжит приходить.

Выключить целиком: `vpn_monitor_alert_enabled: false` и прогон `--tags monitor`. Playbook удалит с сервера и скрипт, и файл с токеном.

## Диагностика

Что происходило с отправками:

```bash
journalctl -t vpn-alert --since today -o short-iso --no-pager
```

Возможные строки:

| Строка | Значение |
|---|---|
| `status=SENT` | Отправлено успешно |
| `status=HELD reason=below_threshold` | `FAIL` есть, но подтверждений пока мало — ждём |
| `status=SKIP reason=no_config` | Файл `/etc/vipen/alert.env` отсутствует: не задан токен |
| `status=SKIP reason=no_token` | Файл есть, но токен пуст |
| `status=SEND_FAILED http=401` | Токен неверный или отозван |
| `status=SEND_FAILED http=400` | Неверный `chat_id` |
| `status=SEND_FAILED http=403` | Вы не нажали Start у бота (шаг 2) либо заблокировали его |
| `status=SEND_FAILED rc=28` | Таймаут: сервер не достучался до Telegram |

Отдельно — дневной отчёт:

```bash
journalctl -t vps-host-daily --since "7 days ago" -o short-iso --no-pager
```

| Строка | Значение |
|---|---|
| `status=OK anomalies=0` | День прошёл чисто, сообщение не отправлялось |
| `status=REPORT anomalies=<N>` | Отчёт сформирован и передан на отправку |
| `status=SKIP reason=notify_unavailable` | Алертинг выключен или не настроен: отчёт остался в журнале |

Проверить, что таймер жив и когда сработает:

```bash
systemctl list-timers vps-host-daily.timer --no-pager
```

Прогнать отчёт вручную, не дожидаясь полуночи (пришлёт данные за вчера):

```bash
systemctl start vps-host-daily.service
```

Токен в журнал не попадает: перед логированием ответ Telegram очищается.

Строки `SKIP` появляются только тогда, когда уведомление действительно требовалось. При здоровом сервере скрипт завершается молча и в журнал ничего не пишет.

Сбросить состояние вручную (например, чтобы получить тревогу повторно):

```bash
rm -f /run/vpn-alert.state
```

## Если Telegram недоступен

Отправка ограничена таймаутом и никогда не влияет на саму проверку: `vpn-notify` при любой ошибке завершается с кодом 0. Мониторинг продолжит работать и писать в journald, даже если Telegram недоступен, токен отозван, а сеть лежит. Потеряется только уведомление — сам health-check от этого не станет менее надёжным.
