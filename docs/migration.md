# Обновление существующего сервера

Изменения после ревью меняют безопасные defaults и процедуру обновления. Не применяйте их сразу ко всем серверам. Рекомендуемый первый шаг — чтение состояния и репетиция на отдельной копии.

## До окна обслуживания

1. Зафиксируйте ОС/архитектуру, текущие версии Docker/Compose, контейнеры, listeners, правила UFW/provider firewall и используемый SSH-порт. Сохраните `docker inspect` приватно: вывод может содержать секреты.
2. Проверьте фактические каталоги БД/сертификатов, Compose project/service и container name. Автоматизация откажется управлять чужим контейнером или неожиданными bind mounts. Для прежнего проекта имя обычно совпадает с basename каталога Compose, но это нужно проверить.
3. Создайте согласованный снимок SQLite и recovery-архив, перенесите их за пределы VPS. Сохраните старый образ через `docker image save`, если нет гарантированного доступа к нему в registry. Проверьте восстановление.
4. Сверьте реальные значения `panel_port`, `xui_panel_path`, пути хранилищ и SSH-порт. Не подставляйте пример production secrets поверх существующих настроек.
5. Изучите [release notes 3x-ui 3.11.0](https://github.com/MHSanaei/3x-ui/releases/tag/v3.11.0). Обновление с 3.3.1 содержит миграции upstream. В лаборатории проверен переход синтетической БД, но БД конкретного сервера может использовать другие функции.
6. Старый администратор с credentials по умолчанию блокирует обновление. Смените его через приватную сессию панели до начала. Новое значение `xui_admin_password` применяется только при создании пустой БД, а не для сброса существующего администратора.
7. Существующая HTTP-подписка требует решения: `xui_subscription_enabled: false` либо сертификат/ключ и явная HTTPS-конфигурация. Действующие клиентские ссылки при переходе могут потребовать обновления.

На первом этапе оставьте `vipen_manage_host: false`, `system_updates_enabled: false`, `network_tuning_sysctl_tuning_enabled: false`, `xui_reality_overrides: []`. Это изолирует обновление приложения от обслуживания ОС.

## Последовательность обновления

Полный удалённый запуск сначала сохраняет и скачивает recovery-архив. Затем deployment helper берёт эксклюзивную блокировку и выполняет:

1. Проверку принадлежности контейнера, целостности и минимальной схемы БД. Явное восстановление поверх существующей БД требует `xui_restore_db_force: true`.
2. Рендер и проверку Compose; загрузку закреплённого образа **до остановки**.
3. Пробную миграцию snapshot через официальный CLI в отдельном контейнере с `--network none`, без capabilities. Все записи остаются в staging-каталоге.
4. Сохранение Compose, сертификатов, manifest и локального image ID. Предыдущий образ получает удерживающий тег `vipen-rollback:deploy-*`.
5. Остановку только сервиса `3xui`, проверку отсутствия writer, обновление recovery snapshot после остановки.
6. Миграцию окончательной копии, транзакционную настройку SQLite и атомарную публикацию БД/Compose.
7. Пересоздание только `3xui` и проверку устойчивого запуска контейнера и loopback-порта панели.

На совпадающих образе, Compose и настройках приложение не перезапускается. Создание очередной резервной копии само по себе считается изменением.

Во время обновления входящие VPN-сессии прерываются. Нужны окно обслуживания и внешний клиентский smoke test после старта. Доступность панели не доказывает работоспособность всех VPN-протоколов.

## Автоматическое и ручное восстановление

Ошибка после остановки запускает возврат: новый writer останавливается, восстанавливается предыдущий snapshot, старый Compose запускается с **предыдущим локальным image ID**. Если старый сервис был остановлен, он остаётся остановленным после возврата. Ошибка rollback сообщается отдельно; нельзя считать её успешным откатом.

Recovery-каталог: `xui_backup_dir/deploy-*/`. Он содержит чувствительные данные и имеет приватные права. `manifest.json` описывает прежний образ/состояние. При потере контроллера, отключении питания или SIGKILL Python не гарантирует автоматический rollback; используйте сохранённую копию и консоль.

Порядок ручного возврата на выделенной копии/в окне обслуживания:

1. Выберите нужный recovery-каталог по manifest. Проверьте БД командой `python3 /usr/local/libexec/vipen/xui_db.py validate /path/to/recovery/x-ui.db`.
2. Остановите только `3xui` с явными `--project-directory`, `-p` и `-f`. Убедитесь через `docker inspect`, что он не Running/Restarting. Не заменяйте БД при работающем writer.
3. Восстановите snapshot через `xui_db.py restore SOURCE DESTINATION`. Helper проверяет source до удаления WAL/SHM и атомарно заменяет БД. Восстановите Compose и сертификаты из того же recovery-набора, если их меняли.
4. Используйте сохранённый `rollback-image.json` либо создайте Compose override с image ID из manifest. Запускайте `docker compose ... -f rollback-image.json up -d --no-deps --pull never --force-recreate 3xui`. Если образ отсутствует, сначала загрузите ранее экспортированный image archive.
5. Проверьте панель, новый SSH-вход, внешний VPN-handshake и передачу данных. Зафиксируйте факт отката, прежде чем снова запускать playbook с новой версией.

При восстановлении на другом сервере перенесите обычные файлы сертификатов отдельно в `xui_cert_dir`, настройте инвентарь, включите `xui_restore_db_enabled` и укажите `xui_restore_db_local_path`. Внешний архив сначала распаковывают в приватный staging-каталог, изучают manifest и проверяют БД; не распаковывайте неизвестный архив непосредственно поверх `/`.

## Перенос владения старыми UFW-правилами

Старая версия использовала общие комментарии `ssh`, `vpn`, `xui-panel` и сбрасывала UFW. Новая версия не может достоверно отличить такие правила от вручную созданных и при `vipen_manage_host: true` останавливается до изменений.

В отдельное окно с консолью сохраните `/etc/ufw` и `/etc/default/ufw`. Сопоставьте каждое старое правило с текущими сервисами и подтвердите принадлежность. Чужие правила оставьте без управляемых меток (замените общий комментарий своим). Для правил Vipen подготовьте новые hash-метки либо создайте актуальные правила и удалите только подтверждённые старые после проверки нового SSH-входа. Hash-метки вычисляет `desired_rules` в `roles/firewall/files/ufw_rules.py`; не присваивайте их чужим правилам. Глобальный `ufw reset` не используется.

Независимый watchdog нового reconciler восстанавливает `/etc/ufw`, `/etc/default/ufw` и прежнее активное состояние через 180 секунд, если новая SSH-проверка не позволила отменить таймер. Он требует работающего systemd. Проверяйте восстановление в лаборатории, особенно IPv6 и provider firewall.

## Смена SSH-порта

Общий playbook отказывает в смене порта. Отдельная процедура:

1. Сохранить доступ по старому порту и добавить новый listener; при socket activation проверить также `ssh.socket`.
2. Разрешить новый порт в UFW и firewall провайдера, оставив старый открытым.
3. Проверить **новое** подключение с внешней машины по ключу, без ControlMaster; проверить IPv4/IPv6 и sudo при необходимости.
4. Обновить `ansible_port`/`ssh_port`, проверить Ansible-доступ и только затем отдельным действием закрыть прежний listener/правило.

Не объединяйте эту процедуру с обновлением 3x-ui.

## Данные для предстоящего production-развёртывания

Потребуются: ОС и версия, архитектура, адрес/домен, SSH-порт и пользователь, способ sudo, fingerprint host key, ограничения сети/VPN/bastion; доступ к консоли провайдера; текущие Docker/Compose и размещённые сервисы; каталоги/имена приложения; список портов и firewall-правил; TLS/домены/продление; размер БД и дисковое место; способ off-host backup и успешный тест восстановления; окно обслуживания, допустимый простой, RPO/RTO и внешний тестовый клиент.

Приватный ключ SSH и production-секреты не присылайте текстом в чат: используйте локальный ssh-agent/защищённый файл и Ansible Vault. До первого изменения production нужен отдельный read-only осмотр и конкретный план применения/возврата для этого сервера.
