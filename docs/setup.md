# Настройка и эксплуатация

## Режимы применения

`vipen_manage_host: false` — режим по умолчанию для существующего сервера. Playbook проверяет входные параметры, создаёт recovery-копию, обновляет приложение и настраивает его резервное копирование и мониторинг. SSH, firewall, Docker daemon, journald и sysctl в этом режиме не меняются. Требуются уже установленные Docker Engine, Compose plugin и системные инструменты мониторинга (`python3`, `bash`, `coreutils`, `util-linux`, `iproute2`, `procps`, `curl`).

`vipen_manage_host: true` включает установку базовых пакетов, SSH-hardening, Docker, UFW/fail2ban и ограничения журналов. Используйте этот режим на выделенном сервере после проверки текущих сервисов. `system_updates_enabled` и `network_tuning_sysctl_tuning_enabled` по умолчанию выключены и включаются независимо.

Целевые платформы: Debian 12/13, Ubuntu 24.04/26.04, systemd, amd64/arm64. Для контроллера установлен диапазон ansible-core 2.20–2.21; воспроизводимая проверенная конфигурация — 2.21.5 на Python 3.14. Статус реальных интеграционных проверок приведён в [testing.md](testing.md).

## Перед первым запуском

1. Подготовьте отдельный контроллер с `requirements-dev.txt`, скопируйте `hosts.example.yml` в `hosts.yml`. Проверьте fingerprint сервера независимым каналом и занесите его в `known_hosts`. Проверка host key включена.
2. Убедитесь, что **новое**, а не переиспользованное SSH-соединение работает по ключу. Для управления хостом playbook проверяет его до изменений. Пустой или содержащий только комментарии `authorized_keys` не принимается.
3. Скопируйте `secrets.example.yml` в `secrets.yml`, задайте `panel_port`. Для нового сервера задайте `xui_admin_username` и случайный `xui_admin_password` длиной не менее 16 символов. Зашифруйте файл через `ansible-vault encrypt`.
4. Для нового выделенного сервера включите `vipen_manage_host: true` и `firewall_manage_defaults: true` в инвентаре. Укажите текущий SSH-порт и свои IPv4/IPv6 сети в `ssh_admin_cidrs`. При отсутствии ограничения список по умолчанию допускает SSH с любого адреса; для production укажите сети администрирования.
5. Подготовьте консоль провайдера, окно обслуживания, свободное место под образ и несколько копий БД/сертификатов. Не выполняйте два применения одновременно на одном сервере.

Если запускаете Ansible локально на сервере, отсутствует независимая проверка SSH с контроллера. Для изменения SSH/firewall требуется `ssh_local_key_login_verified: true` после проверки входа с другой машины и наличие консоли. Предпочтителен удалённый запуск: он также сохраняет копию вне VPS.

Пример инвентаря для нового выделенного сервера:

```yaml
all:
  children:
    vpn_servers:
      hosts:
        vipen:
          ansible_host: 192.0.2.10
          ansible_user: root
          ansible_port: 22
          ansible_ssh_private_key_file: ~/.ssh/vipen
          vipen_manage_host: true
          firewall_manage_defaults: true
          ssh_admin_cidrs: [192.0.2.0/24, "2001:db8::/32"]
```

Адреса выше документальные: замените их своими. Существующие серверы сначала проходят [миграцию](migration.md).

## Применение

```bash
ansible-playbook site.yml --syntax-check --ask-vault-pass
ansible-playbook site.yml --check --ask-vault-pass --limit vipen
ansible-playbook site.yml --ask-vault-pass --limit vipen
```

Без `secrets.yml` разрешена только проверка синтаксиса. `vipen_require_secrets_file: false` предназначен для синтетических тестовых окружений. Не используйте эту настройку на production.

Check mode не создаёт настоящую тестовую инфраструктуру и не проверяет миграцию приложения. Часть подготовительных задач на пустом сервере может не пройти из-за отсутствующих файлов/пакетов. Практическая репетиция проводится в отдельной VM/контейнерной лаборатории.

Полное применение создаёт резервную копию до обновления. Запуск `--tags xui` сохраняет локальную recovery-копию, но пропускает скачивание pre-update архива на контроллер. Для безопасного обновления используйте полный playbook либо `--tags backup,xui,monitor` при выключенном управлении хостом. `--tags firewall` и `--tags monitor` самостоятельно читают актуальное состояние БД.

## Панель и подписки

Панель всегда привязана к `127.0.0.1`. Откройте туннель:

```bash
ssh -N -L 15483:127.0.0.1:54836 -p 22 root@192.0.2.10
```

Замените адрес и порты своими. Браузер обращается к `http://127.0.0.1:15483/<panel-path>/` (либо HTTPS, если сертификат панели уже настроен в БД). Пустой `xui_panel_path` сохраняет текущий путь. При новой установке задайте путь в secrets.yml либо получите его через `docker exec 3xui_app /app/x-ui setting -show` в приватной терминальной сессии. Этот вывод содержит сведения для доступа и не должен попадать в публичные логи.

`xui_subscription_enabled: null` сохраняет существующее состояние подписок. На новой БД подписки выключаются. Уже включённая HTTP-подписка блокирует обновление до явного решения: выключить её либо подготовить TLS. Base64 (`subEncrypt`) не шифрует сетевой трафик.

Для TLS положите сертификат и ключ в `xui_cert_dir`, обеспечьте срок действия и продление отдельно. Файлы монтируются в контейнер только для чтения. Используйте обычные файлы, а не ссылки на внешние каталоги. Затем в зашифрованной конфигурации:

```yaml
xui_subscription_enabled: true
xui_subscription_port: 2097
xui_subscription_cert_file: subscription.crt
xui_subscription_key_file: subscription.key
xui_subscription_uri: https://vpn.example.org:2097/private-path/
xui_subscription_path: /private-path/
```

Firewall открывает фактический порт подписки только при её включении. При `vipen_manage_host: false` соответствующее внешнее правило настраивает оператор. Порт должен отличаться от панели, SSH и включённых VPN-входов.

## VPN-входы и REALITY

Playbook не создаёт входы и клиентов. Пустая новая панель даёт `WARN bootstrap_no_enabled_inbounds`; это состояние первичной настройки. После создания рабочих входов установите `vpn_monitor_expect_inbounds: true`, чтобы их неожиданное отсутствие считалось ошибкой.

`xui_reality_overrides: []` сохраняет существующие значения. Для осознанного изменения:

```yaml
xui_reality_overrides:
  - id: 7
    target: example.org:443
    server_names: [example.org]
```

Можно выбрать по `tag`; порт допускается только если найден ровно один вход. Приватные ключи между записями не копируются, ошибка любого селектора отменяет всю настройку в транзакции. Пробная миграция 3x-ui может вносить собственные изменения схемы — проверяйте клиентское соединение на копии сервера.

## SSH, UFW, Docker и ядро

Общий playbook не меняет SSH-порт: несовпадение с текущим отклоняется. Процедура двухэтапной смены описана в [migration.md](migration.md).

UFW не сбрасывается. Управляются только правила с комментариями `vipen-<12 hex>`. Старые общие метки `ssh`, `vpn`, `xui-panel` требуют ручной сверки принадлежности. Новые разрешения добавляются до удаления устаревших собственных правил. Перед изменениями сохраняются `/etc/ufw` и `/etc/default/ufw`, запускается 180-секундный watchdog. После проверки нового SSH-соединения таймер отменяется. При потере связи дождитесь восстановления и используйте консоль; не запускайте повторное применение вслепую. Проверяйте также provider firewall и IPv6 — UFW их не заменяет.

Docker daemon.json сохраняет сторонние параметры: добавляется только `live-restore`, кандидат проверяется `dockerd --validate`. Параметры ротации логов принадлежат Compose-сервису: `10m`, 3 файла. Новая конфигурация применяется пересозданием только `3xui`, без `--remove-orphans`. NET_RAW удалён, NET_ADMIN не добавляется по умолчанию. Встроенный fail2ban контейнера выключен; host fail2ban обслуживает SSH. Для функций 3x-ui, требующих дополнительных capabilities, отдельно оцените риск host networking.

Установка Docker в режиме provisioning выбирает пакеты stable-репозитория для ОС. Уже установленный Docker Engine не обновляется автоматически. Его версию и совместимость с другими контейнерами проверяют перед отдельным обновлением. `system_updates_enabled: true` обновляет всю ОС и выполняет autoremove: это отдельная операция обслуживания.

BBR загружается перед проверкой доступности. Conntrack нельзя случайно уменьшить: требуется `network_tuning_allow_conntrack_decrease: true`. Изменение qdisc также включается отдельно.

## Резервные копии

`xui-backup.timer` ежедневно создаёт два файла:

- `x-ui.db.auto-<UTC timestamp>` — согласованный SQLite snapshot с integrity_check, права 0600.
- `recovery.auto-<UTC timestamp>.tar.gz` — snapshot, Compose, каталог сертификатов, manifest с ID/ссылкой образа и путями.

Публикация каждого файла атомарная; срок выполнения ограничен. Хранятся последние `xui_backup_keep` пар (по умолчанию 7). Ручные recovery-копии `deploy-*` не удаляются ротацией. Образы в архив не включаются: сохраняйте доступ к registry и отдельно `docker image save` для точного rollback. Если сертификаты являются ссылками, архив содержит ссылки, а не внешние цели; используйте обычные файлы.

На удалённом полном запуске до обновления архив и БД скачиваются в приватный `backups/<host>/<timestamp>/` контроллера. При локальном запуске и у ежедневного таймера копии остаются на диске VPS. Настройте отдельный зашифрованный off-host канал, срок хранения и проверку восстановления. Локальный RPO при ежедневном успешном запуске — до 24 часов; off-host RPO зависит от внешнего расписания, а RTO нужно измерить при восстановлении.

`xui_backup_timer_enabled: false` останавливает таймер и активный worker. При включении обратно проверьте расписание и выполните первый backup вручную, если ещё нет успешной копии.

## Мониторинг и диагностика

`vpn-health.timer` проверяет состояние контейнера, панель, реальные TCP-listeners из БД, Xray при наличии входов, диск, память, conntrack, свежесть backup, systemd, UFW/fail2ban и время. `vpn_monitor_tcp_ports` добавляет дополнительные probes. Команды Docker/systemd ограничены по времени; сервис имеет общий deadline.

Автоперезапуск выключен. Если его включить, рестарт допускается лишь при ошибках приложения, а не только из-за заполненного диска. Диагностический `--no-restart` не меняет счётчик и не отправляет уведомления; его записи имеют отдельный journald tag.

```bash
/usr/local/sbin/vpn-health-check --no-restart
/usr/local/sbin/vpn-healthcheck
journalctl -u vpn-health.service -u xui-backup.service --since today
```

Ручной healthcheck отклоняет отсутствие свежих плановых samples и ошибку чтения журналов. Отчёт `/var/log/vpn-healthcheck-report.log` имеет 0600 и может содержать чувствительные логи приложения.

Выключение `vpn_monitor_enabled`, `vpn_monitor_host_enabled`, `vpn_monitor_host_daily_enabled` останавливает соответствующие workers/таймеры. Эти флаги применяются playbook, простое редактирование файла их не выключает.

Для итоговой оценки VPN нужен внешний клиентский handshake и передача данных, включая IPv4/IPv6 и DNS. Отказ самого VPS обнаруживает внешний heartbeat-контроль. [Настройка оповещений](alerting.md).
