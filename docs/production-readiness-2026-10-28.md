# Повторная проверка перед доступом к production — 28 октября 2026

Это проверка готовности к обследованию сервера, а не отчёт о его состоянии. Адрес и пользователь предоставлены. Две попытки подключения на стандартный SSH-порт 22 завершились сетевым тайм-аутом до SSH handshake и проверки ключа сервером. Команды на сервере не выполнялись; изменений production не было. Нужно уточнить порт и сетевой путь: прямой доступ, VPN/bastion или ограничение источника в firewall.

## Проверенный доступ на контроллере

Файл `~/.ssh/vipen` существует, распознаётся как приватный ED25519-ключ и позволяет получить публичную часть. Права файла — 0600, каталога `.ssh` — 0700. Приватный материал не выводился и в репозиторий не копировался. Корректный файл ещё не подтверждает, что сервер примет этот ключ.

В локальном проекте отсутствуют настоящий инвентарь `hosts.yml`, `secrets.yml` и файл с адресом сервера; подходящей записи SSH config также нет. Переданный адрес не записан в публичные файлы проекта. В `known_hosts` нет записи для этого сервера. При доступности SSH host key нужно сверить с доверенным fingerprint, полученным из консоли провайдера. Подключения выполнялись с обязательной проверкой host key и без пересылки агента.

Версия панели не доказывает версию запущенного Xray: он мог обновляться через панель отдельно. На сервере нужно проверить фактический бинарник, конфигурацию, geo assets и отличия writable layer контейнера от исходного образа.

## Дополнительные условия перед обновлением

Повторная независимая проверка кода выявила ограничения, которые предыдущие synthetic-тесты не закрывали:

1. **Проверка готовности слишком узкая.** Running-контейнер и открытый порт панели не доказывают, что Xray запустился с мигрированной конфигурацией. До production-применения нужно включить проверку сгенерированной конфигурации и процесса/входов в процедуру принятия обновления, а также выполнить внешний клиентский тест.
2. **Может различаться действительное окружение приложения.** Текущий Compose-шаблон содержит фиксированный набор переменных и mounts. Нельзя применять его поверх неизвестных `XUI_DB_TYPE`, `XUI_DB_FOLDER`, NODE_TOKEN_ENCRYPTION, пользовательских mounts и других runtime-настроек. При наличии PostgreSQL или альтернативного SQLite-пути остаточный `x-ui.db` может оказаться не действующей БД.
3. **Одного SQLite-файла недостаточно для всех конфигураций.** Ключ шифрования node tokens, `.env`/`env_file`, дополнительные файлы каталога БД и внешние сертификаты могут быть обязательны для восстановления. Нужно получить список реальных зависимостей, сохранить его вместе с конфигурацией и проверить восстановление.
4. **Image ID не включает изменённый writable layer.** Если Xray/geo-файлы обновлялись внутри старого контейнера, пересоздание из исходного image ID не восстанавливает их точную версию. Следует сохранить используемые assets либо явно перейти на проверенный набор после теста.
5. **Независимая проверка SSH обязательна перед host-hardening.** Ansible rescue не срабатывает при транспортном UNREACHABLE. Снижение MaxAuthTries и несколько ключей в агенте могут привести к отказу нового входа. Нужны проверка с конкретным ключом и независимый механизм возврата перед изменением SSH. По умолчанию `vipen_manage_host: false` оставляет SSH без изменений.
6. **Управление UFW требует дополнительных ограничений.** Добавление идентичного чужому правила с новым комментарием может присвоить его playbook, а последующее удаление помеченного правила — затронуть другой сервис. Сопоставление только по комментариям также не доказывает соответствие действия, порта и обеих IP-семей. Неактивный UFW скрывает сохранённые правила из обычного status. До включения управления host нужно устранить эти случаи и отменять watchdog только после независимой проверки доступа, в том числе при local connection. Эти замечания выявлены при анализе кода; на реальном UFW они пока не проверены.

## Исправления и повторные проверки

Исправлен воспроизводимый дефект rollback: отказ окончательного snapshot после остановки больше не затирает ещё не заменённую БД более ранней hot-копией. Попытка изменения БД и успешная публикация учитываются отдельно. Регрессии проверяют сохранение поздних записей, восстановление окончательной копии при ошибке между удалением WAL и атомарной заменой, а также отказ публикации Compose. До попытки пересоздания rollback запускает исходный контейнер по ID, сохраняя его writable layer; изначально остановленный контейнер остаётся остановленным. Это не закрывает перечисленные выше ограничения после пересоздания и не является гарантией восстановления при SIGKILL или потере питания.

Монитор теперь удерживает shared deployment lock до завершения проверки, включая автоматический restart, если он включён. Это исключает конкуренцию с deployment, которому нужен exclusive lock, и допускает параллельный backup с shared lock. Проверка subscription использует фактический `subListen`, включая IPv6 и wildcard-адреса.

Объединённый запуск после этих изменений: **62/62 теста прошли** в изолированном Bubblewrap-контейнере без внешней сети. Новые проверки используют реальный SQLite, kernel flock из отдельных процессов и реальные локальные IPv4/IPv6 TCP-соединения. Операции Docker/systemd/UFW в регрессиях моделируются: полноценный запуск Docker и обновление этого production-сервера пока не проверены. ShellCheck отрендеренных шаблонов и Black для изменённых Python-файлов также прошли в изоляции.

## Порядок обследования реального сервера

Сначала только чтение: ОС/ядро/архитектура, версии Docker/Compose/панели/Xray, фактические mounts/env/backend, процессы и их происхождение, systemd/таймеры/cron, listeners и соединения, firewall, SSH, состояние дисков, ошибки служб и механизм backup. Неизвестный процесс сам по себе не является лишним: перед остановкой нужно установить владельца, назначение и зависимости.

Затем — согласованная приватная копия действующих данных и полного runtime, сохранение прежнего приложения и образа, проверка восстановления на изолированной копии и сравнение миграции: клиенты, UUID, ключи, входы, лимиты, маршруты, DNS, настройки подписок и аутентификации.

Только после этого выбираются конкретные версии, перечень изменений и процедура возврата для найденной конфигурации. Обновления SSH/firewall/ОС не смешиваются с первым обновлением приложения без доказанной необходимости. Финальная проверка включает доступ снаружи, клиентский handshake и передачу данных.
