# Vipen

[![CI](https://github.com/osipovgit/vipen/actions/workflows/ci.yml/badge.svg)](https://github.com/osipovgit/vipen/actions/workflows/ci.yml)

Ansible-проект для развёртывания [3x-ui](https://github.com/MHSanaei/3x-ui) и мониторинга VPN на Debian/Ubuntu. VPN-входы и клиентов создают через панель или восстанавливают из БД.

По умолчанию Vipen обновляет приложение на уже подготовленном сервере. Управление SSH, UFW, Docker Engine и настройками ОС включается отдельно через `vipen_manage_host: true`. Общесистемные обновления и настройка ядра также требуют отдельного включения.

## Возможности

- 3x-ui **3.11.0**, образ закреплён тегом и SHA-256 digest. Пробная миграция копии БД проходит в контейнере без сети до остановки приложения.
- Обновление сохраняет предыдущую БД, Compose, сертификаты и ID образа. При ошибке после остановки предпринимается возврат к этой паре БД/образ. Это обновление с кратким перерывом, а не zero downtime.
- Панель слушает `127.0.0.1`; доступ — через SSH-туннель. Новая установка требует заданного администратора. Подписки при новой установке выключены; включение требует TLS.
- REALITY-настройки существующих входов сохраняются. Явная правка выбирает ровно один вход по `id`/`tag`; неоднозначный порт отклоняется.
- UFW не сбрасывается: изменяются только правила с собственными метками. При управлении firewall независимый таймер восстановления отменяется после проверки новой SSH-сессии.
- Ежедневные согласованные SQLite-снимки и recovery-архивы с Compose, сертификатами и описанием образа. При удалённом полном запуске копия перед обновлением скачивается на контроллер.
- Мониторинг читает актуальные входы из БД, ограничивает время команд и различает отсутствие данных и исправность. Telegram-уведомления подключаются по желанию.

## Требования и начало работы

Контроллер: Python 3.12–3.14, `ansible-core==2.21.5` (в CI — Python 3.14). Цель: root-доступ по ключу, Python 3, systemd, Debian 12/13 либо Ubuntu 24.04/26.04, amd64/arm64. Разрешённая платформа не означает, что вся матрица прошла интеграционную сертификацию: [покрытие проверками](docs/testing.md).

Перед запуском на существующем сервере прочитайте [порядок миграции](docs/migration.md). Для нового сервера — [инструкцию настройки](docs/setup.md).

```bash
# На отдельном контроллере/в среде разработки:
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements-dev.txt
cp inventories/production/hosts.example.yml inventories/production/hosts.yml
cp inventories/production/secrets.example.yml inventories/production/secrets.yml
# Заполните инвентарь и secrets.yml, затем:
ansible-vault encrypt inventories/production/secrets.yml
ansible-playbook site.yml --syntax-check --ask-vault-pass
ansible-playbook site.yml --check --ask-vault-pass
```

`--check` не выполняет миграцию, pull образа, восстановление и сетевое переключение. Успешный dry run не доказывает успешность обновления. Реальное применение выполняют после проверки копии сервера и подготовки возврата:

```bash
ansible-playbook site.yml --ask-vault-pass --limit vipen
```

Файл `secrets.example.yml` используется только для проверки синтаксиса. Применение без настоящего `secrets.yml` отклоняется. UUID, приватные ключи, БД и ссылки подписок не публикуют в репозитории или issues.
